# AGENTS.md

## Что это за проект

Это backend-сервис на FastAPI.
Проект развивается как модульный монолит: один сервис, но с жёсткими границами между модулями.

Сейчас в проекте уже есть:

- базовый каркас приложения;
- auth для сайта;
- PostgreSQL + Alembic;
- Docker-окружение для локальной разработки;
- API-документация.

## Структура проекта

### Корень

- `app/` — основной код приложения
- `tests/` — тесты
- `migrations/` — Alembic-миграции
- `pyproject.toml` — зависимости и настройки инструментов
- `.pre-commit-config.yaml` — pre-commit проверки

### `app/`

- `app/main.py` — создание FastAPI-приложения
- `app/api/` — общие API-слои:
  - зависимости;
  - глобальный формат ошибок;
  - общие схемы запросов и ответов;
  - корневой router
- `app/core/` — конфиг, БД, логирование, lifecycle
- `app/modules/` — бизнес-модули
- `app/platform/` — platform-level вещи, например plugin SDK, jobs, storage, observability
- `app/shared/` — общие типы и служебные сущности, которые действительно нужны нескольким модулям

### `app/modules/`

Каждый модуль должен развиваться как отдельная область ответственности.

Сейчас `auth` уже содержит:

- `presentation/rest/` — HTTP-ручки;
- `infrastructure/repositories.py` — доступ к БД;
- `service.py` — бизнес-логика;
- `models.py`, `schemas.py`, `security.py`, `contracts.py`.

Для новых модулей и постепенного приведения текущих модулей к одному стилю ориентир такой:

- `domain/` — модели, сущности, value objects, правила предметной области;
- `application/` — service-слой и use cases;
- `infrastructure/` — работа с БД, внешними провайдерами и repository;
- `presentation/rest/` — HTTP-ручки;
- `contracts.py` — внешний контракт модуля для остальных частей приложения.

Текущий код может не полностью совпадать с этой структурой. При новых изменениях двигай проект в эту сторону, а не в сторону случайных плоских файлов.

Если модулю нужен repository, он должен жить внутри этого модуля в `infrastructure/`. Repository вводится по необходимости, когда service-слой начинает зарастать SQLAlchemy-запросами или у модуля появляется устойчивый набор операций чтения и записи. Generic repository на всё приложение не нужен.

## Главные правила разработки

1. Не тащи бизнес-логику в FastAPI router.
   Router должен принимать запрос, валидировать вход, вызывать service/use case и возвращать ответ.

2. Не импортируй внутренности одного модуля в другой напрямую.
   Для межмодульного взаимодействия используй контракты модуля.

3. Не делай `shared` свалкой.
   Туда кладётся только то, что действительно общее для нескольких модулей.

4. Держи единый формат ошибок.
   Не придумывай локальные форматы ошибок внутри отдельных ручек.

5. Любая новая ручка должна быть полноценно описана в API-документации.
   Должны быть понятны:
   - входные данные;
   - выходные данные;
   - статусы ответов;
   - возможные ошибки.

6. Проект использует PostgreSQL и Alembic.
   Если меняется схема БД, должна быть миграция. Перед созданием миграции сначала нормально спланируй модель и связи, чтобы не плодить лишние миграции и быстрые переделки сразу после добавления таблиц.

7. Если меняется поведение кода, обновляй тесты.
   Новое поведение должно сопровождаться тестами, а изменение существующего поведения должно отражаться в уже имеющихся тестах.

8. Развивай проект через модули, а не через один общий service-layer на всё сразу.

9. Сначала фиксируй внешний контракт API и ошибок, потом дописывай реализацию.

10. Если появляется интеграция, провайдер или расширение, не пришивай его прямо к core-логике. Держи границы и раскладывай такие вещи по инфраструктурному или платформенному слою.

11. Не создавай в корне репозитория случайные summary-файлы и временные `.md`/`.txt`, которые не являются частью структуры проекта.

12. Не добавляй новые зависимости без понятной причины.

## Pre-commit

В репозитории уже есть `.pre-commit-config.yaml`.
Сейчас там настроены:

- базовые проверки файлов;
- `black`;
- `isort`.

Перед любым коммитом обязательно:

```bash
pre-commit run --all-files
```

Если `pre-commit` не установлен, его нужно установить, а не пропускать шаг:

```bash
uv tool install pre-commit
pre-commit install
```

## Обязательный workflow

Порядок работы должен быть таким:

1. Внести изменения в код.
2. Обновить или добавить тесты, если изменилось поведение.
3. Отформатировать изменённые Python-файлы:

```bash
uv run black --line-length=100 <changed_files>
uv run isort --profile=black --line-length=100 <changed_files>
```

4. Прогнать тесты.
5. Перед коммитом прогнать:

```bash
pre-commit run --all-files
```

6. Только после этого делать `git commit`.

## Запрещено

Нельзя:

- коммитить код без `pre-commit run --all-files`;
- игнорировать форматирование `Black` с `line-length=100`;
- пропускать обновление тестов при изменении кода;
- говорить, что `pre-commit` недоступен, вместо его установки;
- создавать в корне репозитория случайные summary-файлы вида `.md` или `.txt`, если они не являются частью структуры проекта.
